# TURBO_GORSHOK

## Генератор интеграций с платёжными провайдерами на основе OpenAPI-спецификаций.

Проект автоматизирует создание шаблонов клиентского кода для работы с платежными API, используя декларативные эвристики. Система построена вокруг последовательной обработки данных через несколько слоёв. Наш генератор генерирует: тестовые фикстуры, документацию и сам класс сервиса, наследуемый от базового сервиса.

На диаграмме представлен схематичный процесс генерации сервиса. Отметим, что при генерации фикстур и документации схема такая же, только без использования драйверов и хэндлеров эвристик.

<img width="2924" height="1213"  alt="canvas" src="https://github.com/user-attachments/assets/491d6225-c94c-446d-8f9c-14cb35bb2ba6" />

- **heuristic** – извлечении специфической информации из распарсенной препроцессором OpenAPI спецификации.
- **Preprocessor** – обрабатывает OpenAPI-спецификацию, извлекает и структурирует нужные данные для последующих этапов в виде класса ServiceManifest, который подается пайплайном на вход рендеру.
- **Pipeline** – объединяет этапы генерации в единый поток, управляет порядком выполнения. После окончаниия генерации через Writer сохраняет файлы.
- **heuristic_handler** – реализует специфическую логику применения эвристик к данным и генерирует код.
- **Driver** – отвечает за генерацию конкретного метода/методов на основе результата работы heuristic_handler.
- **Render** – собирает методы, сгенерированные драйверами в единный класс.

Генерация кода была реализована преймущественно за счет ERB шаблонов.

## Добавление нового функционала в генерируемый сервис
- Для генерации нового функционнала необходимо реализовать новый Driver и добавить его в драйверы ServiceRenderer. ServiceRenderer будет передавать ему информацию из класса ServiceManifest и потом добавлять сгенерированный метод в класс сгенерированноо сервиса.
- Если ServiceManifest не достаточно и новый функционал требует специфических информации, которую можно извлечь из голой openAPI спецификации, тогда можно написать свой класс Heuristic (эвристика). Нужно будет добавить написанную эвристику в соответствующий массив в классе препроцессора.
  ```ruby
   HEURISTICS = [CreateEndpointHeuristic, WebhookSigningHeuristic, DigitalSigningHeuristic,
                DataFieldsEncryptionHeuristic].freeze
  ```
- Далее необходимо добавить обработчик для написанной (Handler) эвристики и подключить его к соответствующему драйверу.
- После реализации драйвера, нужно добавить их в Service Renderer.

Добавление новых файлов, например, автотестов, реализуется через создание нового Renderer. После его реализации, его можно подключить в Pipeline.

## Дополнительные доработки для работоспособности в случае тестового примера с YooKassa

- **Корректировка формата `amount`** – в сгенерированном коде `amount` передавался как число (сумма в копейках). API ЮKassa ожидает объект `{ "value": "100.00", "currency": "RUB" }`. Пришлось переписать `build_deposit_payload` и `build_payout_payload`, чтобы формировать правильную структуру.
- **Удаление поля `recipient`** – в тестовом магазине ЮKassa поле `recipient.gateway_id` не требуется, его наличие вызывало ошибку 400. В итоге мы исключили это поле из запросов.
- **Замена Rails-специфичных методов** – сгенерированный код использовал `blank?` и `present?` (из ActiveSupport). Мы заменили их на нативные проверки (`to_s.empty?`) для работы в любом Ruby-окружении без Rails.
- **Реализация `process_callback`** – изначально метод был заглушкой. Мы написали полноценную обработку вебхуков: валидация структуры, извлечение `payment_id` и статуса, маппинг статуса во внутреннее представление.
- **Добавление диагностики** – для отладки добавлен вывод тела ошибки при статусе 400, чтобы быстро идентифицировать проблемы с запросом.
- **Написание HTTP-клиента** – мы реализовали класс `YooKassaClient`, соответствующий ожидаемому интерфейсу (методы `post` и `get` с заданными сигнатурами), используя гем `faraday`.

## Контракты для Operation и Client 

Ниже приведены обязательные требования к объектам, которые передаются в сгенерированный сервис.

## Контракт для `operation` (объект, передаваемый в методы)

Объект `operation` должен отвечать на следующие методы (или быть структурой с соответствующими полями):

| Поле / Метод | Тип | Обязательность | Описание |
|--------------|-----|----------------|----------|
| `id` | String | Да (для идемпотентности) | Уникальный идентификатор операции, используется как `Idempotence-Key` |
| `amount` | Numeric | Да | Сумма операции (в валюте провайдера, например, рубли) |
| `payout_requisite` | Hash | Для выплат | Содержит данные для выплаты: `payout_destination_data`, `payout_token`, `payment_method_id`, `description`, `deal`, `personal_data`, `metadata` |
| `deposit_requisite` | Hash | Для депозитов | Содержит данные для пополнения: `description`, `receipt`, `payment_token`, `payment_method_id`, `payment_method_data`, `confirmation`, `save_payment_method`, `capture`, `client_ip`, `metadata`, и другие (по спецификации ЮKassa) |
| `provider_operation_id` | String | Для `fetch_status` | Идентификатор операции, полученный от провайдера при создании |

**Примечание:** В `payout_requisite` обязательно должно присутствовать поле `deal.id` – оно должно быть строкой длиной от 36 до 50 символов (проверяется в `check_conditions`). Для депозита это поле не проверяется.

## Контракт для HTTP-клиента (`client`)

Клиент, передаваемый в конструктор `BaseService` (и наследуемый сервисом), **должен реализовывать ровно два публичных метода**:

### `post(url, json: nil, headers: nil)`

| Параметр | Тип | Описание |
|----------|-----|----------|
| `url` | String | Полный URL запроса (включая базовый URL провайдера) |
| `json` | Hash (опционально) | Тело запроса в формате JSON (будет сериализовано в JSON) |
| `headers` | Hash (опционально) | HTTP-заголовки (например, `Authorization`, `Idempotence-Key` и др.) |

**Возвращаемое значение:** объект, который отвечает на:
- `status` – целочисленный HTTP-код ответа.
- `body` – распарсенный JSON-ответ (Hash или Array).

---

### `get(url, headers: nil)`

| Параметр | Тип | Описание |
|----------|-----|----------|
| `url` | String | Полный URL запроса (с путём и параметрами) |
| `headers` | Hash (опционально) | HTTP-заголовки |

**Возвращаемое значение:** объект, аналогичный возврату `post` (с полями `status` и `body`).

---

## Дополнительные требования к клиенту

- Клиент **не обязан** обрабатывать сетевые исключения – сгенерированный сервис сам перехватывает ошибки и преобразует их в объект `failure`
- Клиент должен корректно сериализовать тело запроса в JSON и парсить ответы, если они приходят в формате JSON.

# Обработка сложных циклических зависимостей OpenAPI спецификации

Ближе к концу хакатона протестировали наше решение на OpenAPI пецификации т-банка и код упал с ошибкой парсера - гема, который мы используем не способен разрешать сложные циклические зависимости. Нашли решение этой пробоемы - в таких случаях следует предобработать openAPI спецификацию с помощью Swagger.

Предположим, что спецификация, падающая с ошибкой называется openapi.yaml .

Тогда следует выполнить следующие команды и после этого наш парсер заработает.

```bash
npx @apidevtools/swagger-cli bundle yaml_examples/openapi.yaml -o yaml_examples/openapi.yaml --dereference

ruby fix_schema.rb yaml_examples/openapi.yaml
```
